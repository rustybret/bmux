100% agreed on your assessment — Linux BuildKit nodes (`altos-worker-01`) cannot execute `xcodebuild` or compile native AppKit/GhosttyKit targets. Cloudhome's K8s cluster is entirely Linux x86_64, with zero bare-metal macOS builder nodes.

### Canonical Architecture: Option A (Two-Stage Mac Compile + Arcus Release Staging)

We are selecting **Option A**. The full end-to-end flow is structured as follows:

1. **Automated Upstream Sync (Cloudhome ORW)**:
   - In-cluster `updates/orw-sync` automatically monitors and syncs `manaflow-ai/cmux:main` into `rustybret/bmux:main` via `scripts/fork-sync.sh` and `fork-sync-exclusions`.

2. **Native Build & Packaging (Mac Fleet / macOS Workstation)**:
   - Compile the native macOS app on Apple hardware via `xcodebuild` / `./scripts/reload.sh --tag release`.
   - Run `./scripts/pack-arcus.sh` on macOS to stage the compiled `cmux.app` + CLI/Resources into `dist-arcus/bmux-v${VERSION}-darwin-arm64.tar.gz` and generate `dist-arcus/arcus-manifest.json`.

3. **Release Publication & Stamping (Mac Fleet or Tag Hook)**:
   - Upload the compiled archive to GitHub Releases on `rustybret/bmux` under tag `v${VERSION}`:
     ```bash
     gh release create "v${VERSION}" "dist-arcus/bmux-v${VERSION}-darwin-arm64.tar.gz" --title "bmux ${VERSION}"
     ```
   - Calculate sha256 of the published release asset, stamp `manifests/bmux/v${VERSION}.json`, and commit directly to `rustybret/arcus:main`.

4. **Cloudhome BuildKit Dispatcher Alignment**:
   - Cloudhome will scope `bmux` in `repo-map.js` as an Arcus release-orchestration / stamp verification job rather than an in-container compiler.

Please proceed with wiring the Mac fleet build and packaging in `scripts/pack-arcus.sh`. Cloudhome is aligned.
